# AIPO Backend Rules

## 1. 목적
이 문서는 AIPO 백엔드 구현 시 따라야 할 실무 규칙을 정리한 초안이다.
설계서의 기능 범위와 요구사항 정의서의 데이터 항목을 실제 코드 구조에 반영하기 위한 기준으로 사용한다.

## 2. 계층 분리 원칙
- Controller는 요청/응답 변환과 인증 정보 수집에 집중한다.
- Service는 유스케이스 단위의 비즈니스 로직을 담당한다.
- Repository는 조회/저장 책임만 가진다.
- External client는 공시/증권 API, AI 엔진, 벡터 DB 연동을 담당한다.
- Batch/Scheduler는 데이터 수집과 문서 인덱싱 작업을 담당한다.

## 3. 모듈 분리 원칙
권장 모듈:
- auth
- profile
- ipo
- watchlist
- calendar
- chat
- admin
- pipeline
- rag
- common

현재 프로젝트 구조가 이미 존재하면 기존 구조를 우선하고, 새 모듈 추가는 최소화한다.

## 4. 인증/인가 규칙
- 사용자와 관리자의 인증 흐름을 분리한다.
- 관리자 API는 user 토큰으로 접근할 수 없게 한다.
- 로그아웃은 단순 화면 전환이 아니라 서버 기준 무효화 정책을 검토한다.
- 회원탈퇴/사용자삭제/문서관리 같은 기능은 권한 검증을 반드시 포함한다.

## 5. API 규칙
- 목록 조회는 pagination/filter/sort 확장 가능성을 고려한다.
- 상세 조회는 화면 구성 단위를 반영한 DTO를 사용한다.
- 검색 API는 검색어 없을 때 기본 조회 정책을 명확히 한다.
- 정렬 기준은 enum 또는 검증 가능한 문자열 정책으로 관리한다.
- 빈 결과와 오류 결과를 구분한다.
- 공통 예외 포맷이 있다면 반드시 재사용한다.

## 6. 응답 설계 규칙
- 종목 목록 응답에는 상세 이동이 가능한 식별자를 포함한다.
- 종목 상세 응답은 적어도 다음 영역을 구분할 수 있어야 한다:
  - 기본 정보
  - 공모 정보
  - 기업 정보
  - 경쟁률
  - 수요예측
  - 매력지수
  - 관심 종목 상태
- 챗봇 응답은 답변 본문, 근거/출처, 세션 정보, 피드백 가능 여부를 고려한다.
- 관리자 통계 응답은 차트 렌더링이 쉬운 구조를 우선한다.

## 7. 데이터 규칙
- 사용자 투자 성향은 별도 필드 또는 별도 엔터티로 관리한다.
- 관심 종목 정렬 순서와 알림 설정은 사용자-종목 관계 데이터로 관리한다.
- 일정 데이터는 날짜/유형/종목 기준으로 조회 가능해야 한다.
- 채팅 기록은 세션과 메시지를 분리하는 방향을 우선 검토한다.
- 답변 평가는 답변 ID 기준으로 추적 가능해야 한다.
- 참고 문서는 문서 ID와 버전 정보를 함께 관리한다.

## 8. AI / RAG 연동 규칙
- 문서 업로드 → 텍스트 추출 → 청크 생성 → 임베딩 → 벡터 저장 흐름을 분리한다.
- 사용자 질문 처리와 문서 인덱싱 처리를 같은 트랜잭션 성격으로 섞지 않는다.
- 챗봇 답변에는 가능하면 근거 문서 메타데이터를 포함할 수 있도록 준비한다.
- “모르는 것은 모른다고 답함” 정책을 손상시키는 임의 후처리를 피한다.
- 사용자 피드백 데이터는 모델 개선용 로그로 누적 가능해야 한다.

## 9. 운영/관리 규칙
- 외부 API 상태, 크롤링 상태, 수동 호출 이력은 추적 가능해야 한다.
- 관리자 로그 조회 시 개인정보 마스킹을 고려한다.
- 집계 통계는 실시간 계산과 사전 집계 중 어떤 방식을 쓰는지 명확히 한다.
- 마지막 갱신 시각과 업데이트 주기는 사용자/관리자 화면 양쪽에 활용 가능해야 한다.

## 10. 테스트 규칙
- 인증 성공/실패
- 검색 결과 있음/없음
- 관심 종목 등록/해제 중복 처리
- 캘린더 월 조회와 날짜별 상세
- 챗봇 세션 생성과 기록 조회
- 관리자 권한 없는 접근 차단
- 문서 업로드 및 인덱싱 상태 변화
위 항목은 최소 테스트 후보로 간주한다.

## 11. Codex 작업 규칙
Codex에게 작업을 요청할 때는 다음 순서를 권장한다.
1. 관련 기능 범위 요약
2. 변경 파일 목록 제안
3. DTO 초안
4. 서비스 책임 정리
5. 컨트롤러/레포지토리 구현
6. 테스트 포인트 요약

## 12. 추천 프롬프트 샘플
### 기능 파악
`설계 문서를 기준으로 공모주 상세 조회 기능의 관련 도메인과 백엔드 책임을 먼저 정리해줘. 아직 코드는 수정하지 마.`

### 변경 계획
`현재 backend 코드 기준으로 공모주 상세 조회를 구현하려면 어떤 파일을 수정해야 하는지 먼저 계획만 제안해줘.`

### 작은 단위 구현
`종목 상세 기능 중 response DTO와 매퍼만 먼저 구현해줘. 기존 패키지 구조를 유지하고 서비스 로직은 건드리지 마.`

### 문서 비교
`설계 문서와 현재 backend 코드를 비교해서 이미 구현된 것과 아직 없는 것을 체크리스트로 정리해줘.`

### 관리자 기능 구현
`관리자 대시보드의 활성 사용자 수 조회 기능만 구현하려고 한다. API 설계와 서비스 책임을 먼저 정리해줘.`
